# Method library → idea optimizer handoff

## Select and pass

Use the user's base idea and question to search `index.md` by architectural bottleneck, module role, intervention point, interfaces, and transfer tags. Read only the relevant full cards. Pass the cards to `ccf-idea-optimizer` for an explicit idea task or when a newly added reference belongs to an existing idea workspace for the same research direction. In the latter case, update that workspace's memory and active idea after the method card is complete; stop after card creation when the user explicitly requests paper archiving only. The handoff names the library root, selected card paths and source versions, card completion status, source-supported architectural explanations with anchors, inferred transfer hooks, and unresolved architecture requirements. The optimizer should be able to reason from the card's explanation without reconstructing the method from a list of PDF citations; reopen the source only for a consequential unknown or verification. A card describes its original paper; it does not establish that a new combination will work.

If a selected card is partial, its source version has changed, or an architecture requirement is missing, record the affected requirement as `unknown` during idea discussion. Do not refresh or write back a method card as part of that discussion. Refresh source-grounded architecture fields only in a separate paper-processing task or an authorized combined workflow, including the standing project instruction to pass newly added references into an existing same-direction idea workspace. Do not reprocess unchanged PDFs merely because the base idea changes. Details such as preprocessing, objective, training, inference, or empirical evidence remain outside the card's scope unless they determine an architectural transfer condition; mark unreviewed requirements unknown instead of assuming compatibility. If external novelty claims matter, `ccf-literature-searcher` checks closest work separately.

## Compatibility before composition

`ccf-idea-optimizer` compares the base idea and each selected mechanism at the architecture level: task-facing inputs and outputs, model topology or insertion point, module roles and information flow, interfaces, and structural assumptions. Record `compatible`, `conditional`, `conflict`, or `unknown` with a concrete reason and a relevant card/source anchor. Treat requirements outside a card's stated scope as `unknown`; a missing implementation detail is not evidence of compatibility.

For a conditional fit or conflict, specify a proposed **bridge mechanism**: what adapts an input, output, or structural assumption; what information flow or architectural behavior it creates; and which premise remains to be established. Keep source-supported operations, the user's base mechanism, and the optimizer's new inference traceable as separate parts. A mere sequence of existing modules is not a bridge.

The optimizer develops candidate frameworks and their discriminating tests under its own skill rules. Its output cites selected card IDs and source anchors, states material architecture unknowns, and identifies the simplest comparison that could falsify a central interaction claim. The optimizer owns its evolving idea records and discussion-derived interpretations. Do not write a candidate framework, bridge mechanism, or new interpretation into a source method card or its index as part of this handoff. Revise a method card only in a distinct method-card task, with source verification for each changed source claim.
